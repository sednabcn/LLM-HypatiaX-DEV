Four architectures for running HypatiaX on AWS — pick the one that fits.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Architecture 1 — Cheapest: Spot EC2 + user-data script (~$1/run)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
How it works: You launch one r6i.xlarge Spot instance manually. It runs the
full pipeline via a user-data bootstrap script, uploads results to S3, then
self-terminates. You SSH in only if something goes wrong.

What you need:

  # 1. Create an S3 bucket for results
  aws s3 mb s3://hypatiax-results

  # 2. Create an IAM role with S3 write + Secrets Manager read +
  #    self-terminate permissions
  # (policy: s3:PutObject on your bucket,
  #           secretsmanager:GetSecretValue on your secret,
  #           ec2:TerminateInstances on self)

  # 3. Store the Anthropic API key in Secrets Manager
  aws secretsmanager create-secret \
    --name hypatiax/repro/anthropic-key \
    --secret-string "sk-ant-YOUR-KEY" \
    --region us-east-1

  # 4. Launch the instance
  aws ec2 run-instances \
    --image-id ami-0c02fb55956c7d316 \      # Amazon Linux 2023, us-east-1
    --instance-type r6i.xlarge \            # 4 vCPU, 32 GB RAM
    --instance-market-options '{"MarketType":"spot"}' \
    --iam-instance-profile Name=hypatiax-runner \
    --user-data file://bootstrap.sh \
    --block-device-mappings '[{"DeviceName":"/dev/xvda","Ebs":{"VolumeSize":80,"VolumeType":"gp3"}}]'

  # bootstrap.sh runs the full CI v9 pipeline — see hypatiax-reproducibility.yaml
  # UserData section for the reference implementation.

Cost: ~$0.08–0.12/hr × ~5 hours = ~$0.50–0.60 compute + S3 negligible.
Total ~$1. Spot interruption risk ~2% for r6i.xlarge in us-east-1.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Architecture 2 — Fully automated: GitHub Actions → AWS CodeBuild
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
How it works: Your existing CI YAML stays. The memory-heavy Phase 1 jobs
dispatch to AWS CodeBuild instead of GitHub-hosted runners. CodeBuild uses an
r6i.xlarge-equivalent environment with 32 GB RAM.

In CI v9, exp2 is a single sequential job (--protocol all30 --resume) — there
is no sharding. The most practical CodeBuild dispatch point is exp2 itself,
which needs 32 GB and runs for up to 340 minutes.

Key change to ci-aws.yml — dispatch exp2 to CodeBuild:

  exp2:
    name: "exp2 · 6-method comparison suite (all30)"
    runs-on: ubuntu-latest          # ← orchestrator stays on GitHub
    needs: exp2-hyb
    steps:
      - uses: actions/checkout@v5
      - name: Trigger CodeBuild
        uses: aws-actions/aws-codebuild-run-build@v1
        with:
          project-name: hypatiax-exp2
          env-vars-for-codebuild: |
            ANTHROPIC_API_KEY,PYSR_TIMEOUT,LLM_MODEL
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          LLM_MODEL: claude-sonnet-4-20250514
          AWS_REGION: us-east-1
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

CodeBuild project config (buildspec.yml):

  version: 0.2
  env:
    secrets-manager:                        # Secrets Manager, not SSM
      ANTHROPIC_API_KEY: hypatiax/repro/anthropic-key
  phases:
    install:
      commands:
        - pip3.12 install -r requirements.txt
        - curl -fsSL https://install.julialang.org | sh -s -- --yes --no-modify-path
        - export PATH="$HOME/.juliaup/bin:$PATH"
        - juliaup add 1.11 && juliaup default 1.11   # pin to match CI
    pre_build:
      commands:
        - aws s3 cp s3://hypatiax-results/checkpoints/ logs/ --recursive || true
        - aws s3 cp s3://hypatiax-results/checkpoints/exp2_all30_checkpoint.json \
            hypatiax/data/results/comparison_results/ || true
    build:
      commands:
        - export JULIA_NUM_THREADS=4
        - export LLM_MODEL=claude-sonnet-4-20250514
        - python3.12 run_all_checkpoint.py --only exp2 --resume --continue-on-fail
    post_build:
      commands:
        - aws s3 sync logs/ s3://hypatiax-results/checkpoints/
        - aws s3 sync hypatiax/data/results/ s3://hypatiax-results/results/
  artifacts:
    files:
      - hypatiax/data/results/comparison_results/exp2_all30_checkpoint.json

CodeBuild compute type: BUILD_GENERAL1_2XLARGE (8 vCPU / 15 GB) covers most
jobs. For exp2 and exp1 chunks that require the full 32 GB, use
BUILD_GENERAL1_LARGE2 (16 vCPU / 64 GB) or run on a self-hosted runner
(Architecture 3). Cost: ~$0.30/hr, billed only while building.

Why this works: your CI graph, caching, artifact handling, and pass/fail logic
all stay in GitHub Actions. Only the compute moves to AWS.

Architecture 3 — Hybrid: self-hosted GitHub Actions runner on EC2
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
How it works: An EC2 instance registers itself as a GitHub Actions runner with
the labels [self-hosted, linux, aws-c5-4xlarge] — exactly matching the
runs-on values already in ci-aws.yml v9. Your CI YAML needs zero changes.

  # On the EC2 instance (c5.4xlarge — 16 vCPU, 32 GB RAM, matches CI label):
  mkdir actions-runner && cd actions-runner
  curl -O -L https://github.com/actions/runner/releases/download/v2.322.0/actions-runner-linux-x64-2.322.0.tar.gz
  tar xzf actions-runner-linux-x64-2.322.0.tar.gz

  # Register (get token from GitHub → Settings → Actions → Runners → New runner)
  ./config.sh \
    --url https://github.com/YOUR_ORG/LLM-HypatiaX-PAPERS-Public \
    --token YOUR_REGISTRATION_TOKEN \
    --labels "self-hosted,linux,aws-c5-4xlarge" \
    --name hypatiax-ec2

  # Run as a service
  sudo ./svc.sh install && sudo ./svc.sh start

The ci-aws.yml jobs already specify:
  runs-on: [self-hosted, linux, aws-c5-4xlarge]

No changes to the YAML at all — just register the runner with the matching
labels and push. All 74 exp1 case chunks, exp1b, exp2-feynman, exp2-sym,
exp2-hyb, exp2, exp3, exp3b, supp, audit, and output jobs route automatically
to the EC2 runner.

Pros: zero YAML changes, full 32 GB RAM, no CodeBuild setup.
Cons: you pay for the instance even when idle unless you add auto-start/stop
via Lambda + GitHub webhooks (recommended for long review periods).

Architecture 4 — One-click for reviewers: AWS CloudFormation stack
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
For paper reproducibility. You publish hypatiax-reproducibility.yaml once.
Reviewers click "Launch Stack" and get results — no CLI, no SSH, no Julia
installation, no API key handling.

What a reviewer does:
  1. Click the "Launch Stack" badge in the README or paper supplementary
  2. Land on the AWS CloudFormation console (free AWS account is the only
     prerequisite)
  3. Leave all parameters as-is (PysrTimeout, RepoBranch, InstanceType,
     SpotMaxPrice — defaults match the paper)
  4. Tick "I acknowledge that AWS CloudFormation might create IAM resources"
  5. Click Create Stack
  6. Open the Outputs tab → click the ResultsWebsite URL
  7. Page shows live progress while the pipeline runs (~4–6 hours)
  8. Refresh — results table + ZIP download appear when done

Reviewers never touch an API key. It is maintained by the authors in Secrets
Manager and pulled at runtime.

Architecture overview:

  Reviewer clicks URL
         │
         ▼
  CloudFormation Stack (hypatiax-reproducibility.yaml v3 / CI v9)
    ├── IAM Role          (EC2 + S3 + Secrets Manager, least-privilege)
    ├── S3 Bucket         (results + static website, auto-deletes after 45 days)
    ├── Secrets Manager   (Anthropic API key — authors maintain, reviewers never see)
    ├── EC2 Spot Instance (r6i.xlarge, 32 GB, 4 Julia threads, self-terminating)
    │     └── user-data bootstrap (Python 3.12 · Julia 1.11):
    │           install deps → julia 1.11 (juliaup) → PySR warmup
    │           → fetch key from Secrets Manager
    │           → Phase 0: validate
    │           → Phase 1: exp1 (74 cases) · exp1b · exp2-feynman ·
    │                      exp2-sym · exp2-hyb · exp2 (all30) · exp3 · exp3b
    │           → Phase 2: suppB · suppA · instability · extrap
    │           → Phase 3: provenance · discover-provenance ·
    │                      scan-imports · verify · hashlock
    │           → Phase 4: figures · tables
    │           → generate HTML report + ZIP → upload to S3 → self-terminate
    └── CloudFormation Output → ResultsWebsite URL (live from boot)

Everything is created fresh per reviewer run and destroyed when done.
No shared state, no cleanup burden on the reviewer.

The three files to publish:
  File 1 — hypatiax-reproducibility.yaml  (the CloudFormation template)
  File 2 — REPRODUCIBILITY.md            (drop in repo root; has Launch badge)
  File 3 — Makefile.repro                (author operational runbook)

Given your 3.8 GB local machine and the pipeline structure in ci-aws.yml v9:

Use Architecture 4 (CloudFormation) for reviewer reproducibility — it is
already built and published as hypatiax-reproducibility.yaml v3. Reviewers
get one-click access with no API key handling required.

Use Architecture 3 (self-hosted runner) for your own development workflow.
ci-aws.yml v9 already targets [self-hosted, linux, aws-c5-4xlarge] on every
job — register a c5.4xlarge EC2 instance with those labels and git push
triggers the full pipeline automatically.

The two things you need regardless of architecture:

  # 1. S3 bucket for results / template hosting
  aws s3 mb s3://hypatiax-results --region us-east-1

  # 2. Anthropic API key in Secrets Manager (not SSM)
  aws secretsmanager create-secret \
    --name hypatiax/repro/anthropic-key \
    --secret-string "sk-ant-YOUR-KEY" \
    --region us-east-1

Everything else — IAM roles, security groups, the bootstrap script, the
HTML report, the ZIP, key rotation — is handled by the CloudFormation template
and Makefile.repro.

API key rotation (no template republish needed):
  aws secretsmanager update-secret \
    --secret-id hypatiax/repro/anthropic-key \
    --secret-string "sk-ant-YOUR-NEW-KEY"
  # Reviewers who launch after this automatically get the new key.
  # Reviewers mid-run are unaffected — key was fetched at boot.
