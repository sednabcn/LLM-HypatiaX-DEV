Why I prefer this design
Your provenance map is already the canonical record of:

    • the seed, 
    • and the output files. 
If every experiment has a similar provenance file, you gain:
    • a single source of truth for locating results, 
    • traceability from every table back to the exact experiment configuration, 
    • and a clean separation between experiment-specific parsing and paper-specific formatting. 
I think this is a more maintainable solution than hardcoding directory searches or creating a new runner solely for table generation.

the prolem is using a single metric
I think you've identified the real design problem.
The issue is not that gen_five_system() can't find the data—it's that Table 1 tries to compare fundamentally different systems using a single metric.
For example:
System	Natural output
Neural Network	Prediction accuracy (RMSE, MAE, R²)
Symbolic Regression	Formula + prediction accuracy + complexity
Pure LLM	Generated expression, success rate, validity
Hybrid	Formula + accuracy + search cost
LLM + Fallback	Formula + accuracy + fallback rate
A single metric like "extrapolation error (%)" unfairly favors or penalizes some systems because they have different objectives and outputs.
I would redesign the comparison
Instead of one metric, define a common evaluation schema with multiple dimensions.
For example:
System	Valid	Train R²	Test R²	Extrapolation	Formula	Runtime
Pure LLM	✓	—	0.72	410%	✓	2 s
Neural Net	✓	0.99	0.94	85%	✗	8 s
Symbolic	✓	0.97	0.95	61%	✓	210 s
Hybrid	✓	0.99	0.98	24%	✓	95 s
Now every system is judged on the aspects it can actually provide.
Even better: define metric categories
Instead of one "score", organize metrics into categories:
Predictive Performance
    • RMSE
    • MAE
    • R²

Extrapolation
    • Mean error
    • Median error
    • 95% CI

Interpretability
    • Formula recovered
    • Expression complexity
    • Exact match

Efficiency
    • Runtime
    • API calls
    • Memory
Each experiment can populate the applicable metrics, while the table generator renders the same structure consistently.
If the paper still needs a single ranking
If reviewers require one overall ranking, I would not invent a weighted score. Instead, use a multi-criteria approach:
    • Report each metric separately. 
    • Highlight the best value in each column. 
    • Let readers see the trade-offs. 
This is much more transparent and avoids arbitrary weighting.
My suggestion
Rather than trying to force every experiment into a single metric, refactor the pipeline around a canonical result schema that stores all relevant metrics for each method. Then gen_five_system() can select the subset of metrics appropriate for a particular table.
That way:
    • The experiments remain faithful to what they measure. 
    • The tables are reproducible. 
    • You can generate different comparison tables (accuracy-focused, efficiency-focused, interpretability-focused) from the same underlying JSON without rerunning experiments. 
I think this approach is both scientifically stronger and easier to maintain than trying to make every system fit one metric.

The key takeaway
Since you've confirmed that all data originated from exp1b, the right architecture is:
    1. Make exp1b produce a complete five_system_results.json. 
    2. Include successful evaluations and structured failure records. 
    3. Have gen_five_system() render whatever is present in that JSON—numbers for successful runs and status/reason for unsuccessful ones. 
    4. Eliminate all hardcoded values and fallback logic. 
That preserves reproducibility and accurately reflects the experiment without conflating "not evaluated" with "no result."
