Honestly, I'd flag this as a good instinct with a real fairness problem hiding in it. Breaking it into what's sound and what isn't:
What's genuinely good about it
    • The 4 protocols already stress different failure modes on purpose: DeFi is extrapolation-heavy (ratio/product formulas, adversarial splits, the moneyness/clamping bugs you saw fixes for), Feynman/benchmark_v2 is broad-domain coverage, Nguyen-12 is the canonical SR benchmark literature compares against, all_30 is multi-domain breadth. Running the same variant set across all four would genuinely tell you whether a variant's gate logic is a real idea or an overfit to one dataset's quirks — which is a legitimate and valuable thing to know. 
    • The registry pattern (BaseMethod + METHOD_REGISTRY) is already built for exactly this kind of extension. Adding entries is cheap once a variant conforms to the interface. 
Where it breaks down
    1. These aren't one pipeline today — they're three disjoint ones with non-overlapping variant coverage. DeFi protocol only ever runs the v4 selector (Variant 6/6-PCA). Feynman protocol runs Variants 1, 2, 4, 5 via the registry. Nguyen-12 runs Variant 7's raw-PySR-plus-guesses flow, which doesn't use the registry at all. "Compare all variants across all 4 protocols" isn't retrofitting a config flag — it's building new adapters for variants that were never designed against that protocol's data shape. 
    2. Some variants don't have an honest way to run on some protocols. Variant 7 seeds PySR's genetic search population — DeFi's pipeline doesn't use PySR at all, it trains a plain NN. To run Variant 7 on DeFi you'd have to bolt PySR onto a pipeline that was never validated with it. Variant 6's selector is built around DeFi-specific candidates (residual_nn, the extrapolation-domain linear fallback) — porting it to Feynman means redeciding what "extrapolative" even means in that feature space. That's not wiring, that's redesigning the variant. 
    3. The repo's own history is a warning here. Half the "Fix N" comments you've been reading (moneyness, extrapolation guard, PCA split parity) exist because logic built for one context got reused in another without re-deriving whether the assumptions still held. Forcing all 9 variants through all 4 protocols mechanically is the exact pattern that produced those bugs the first time. 
    4. A single leaderboard across protocols would be statistically misleading. 74 DeFi cases, ~30 Feynman-domain equations, 12 Nguyen equations — different denominators, different noise regimes, different what-counts-as-success thresholds (the v4 benchmark file is explicit about this: "all aggregate R²>0.99 rates use a FIXED denominator of 74... previous headline figures used different per-method denominators and are NOT comparable"). Averaging R² across protocols would repeat that exact mistake at a larger scale. 
    5. Cost compounds badly. 9 variants × 7 experiments × real case counts × multiple seeds, with several variants calling the Anthropic API per case and PySR-backed methods running genetic search per case — this is the API-budget/wall-clock concern I flagged last time, multiplied by "now every variant runs everywhere" instead of "each variant runs where it already belongs." 
What I'd actually recommend
Don't force uniform coverage. Instead:
    • Run each variant only on the protocol(s) it's actually built for (Variant 7 → Nguyen-12 only, Variant 6/6-PCA → DeFi only, Variants 1–5 → whichever already have registry entries), and report per-protocol, not pooled. 
    • Where you do want cross-protocol signal — e.g. "does the R²-threshold-gate family (1, 4) generalize better than the validation-selection family (6)?" — pick the 2–3 variants that share a compatible interface and are meaningful on a given protocol, rather than running all 9 everywhere. 
    • Treat "port Variant X to protocol Y" as its own reviewed task with its own fidelity check (like the standalone scripts I built you, verified against real source), not a side effect of a CI matrix expansion. 
If that reframing works for you, it also simplifies the plan I gave you — decision #1 (is Variant 7 Nguyen-12-only) becomes "yes, and that's fine," and the registry extension in Phase 1 only needs to cover the variant/protocol pairs that are actually valid, not a full 9×4 cross product.
