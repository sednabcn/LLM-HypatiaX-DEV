How value drift is managed
Three mechanisms, demonstrated above:
    1. The manuscript is never the source of truth for "what value is currently there" — applied_log.json is. After every real apply, the runner records {new_str, value, source, timestamp} and appends it to a per-item history (never overwrites). On the next run, it searches the file for the last-applied text, not the pristine old_str from the manifest. So a second round of patching still finds its target even though the original old_str no longer exists in the file.
    2. A changed value never overwrites silently. Round 2 above: a fresh investigation returned 312.9 instead of the already-applied 841.4. The runner detected prior_value != value, refused, and printed exactly what changed and why ('841.4' (from investigate_item3_runtime.py) -> '312.9' (from investigate_item3_runtime.py)). Nothing gets overwritten until you explicitly pass --allow-value-change — same asymmetry as --apply itself: dry-run is the default for new patches, explicit confirmation is required for changing an already-landed one.
    3. Full provenance survives, not just the final number. applied_log.json's history list keeps every value this item has ever held, with its source and timestamp — so if a value flips twice (like the HDS 22/30 → 23/30 → 27/30 progression last time), you can see the whole chain, not just today's number. Combine that with a git commit per --allow-value-change application and you get the same auditable trail as the Phase 3 report's "Stage 0 / Stage 1 / Stage 2" supersession structure — except automatic instead of hand-written.
The one thing this doesn't try to automate is judging whether a new value should be trusted — that's still a human call (or a rule you encode per-item, e.g. "only accept values from a real-stack GitHub Actions run, not a sandbox estimate"). It just guarantees the tool can't quietly clobber a good number with a worse one.
