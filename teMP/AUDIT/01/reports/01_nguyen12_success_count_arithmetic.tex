% PySRRegressor or .fit() — both the `if llm_exprs:` and `else:` branches

% no differentiating input and a deterministic solver, the two arms were
% guaranteed to converge to identical results. This is a warm-start
% injection bug, not the ground-truth-leak pattern documented in
% run_all.sh for exp1/exp1b/hybrid_all_domains (that leak is a different
% mechanism — target formula reaching the LLM prompt — and exp3 has not

% Round 4 (hypatia.py reviewed — two follow-on findings):
%
%   a. GT-LEAK CHECK (was item 2, open last round): hypatia.py's
%      _build_prompt() only reads eq["formula_hint"]; it never touches
%      eq["formula"] (the ground-truth expression also present in exp3's
%      eq_dict). So get_llm_prior() does NOT leak the full ground-truth
%      formula into the LLM prompt the way run_all.sh documents for

%      pattern. Residual gap: formula_hint's actual content is defined in
%      NguYenProtocol, which is still not in this checkout, so it can't
%      yet be confirmed that formula_hint itself is answer-free.
%
%   b. SYNTAX MISMATCH (new, found while implementing (a)'s neighbor):
%      the guesses=llm_exprs patch from the previous round was itself
%      broken. get_llm_prior() returns Python/numpy-syntax expressions
%      ("x**3 + x**2", "np.sin(x) + x"), but this script's PySR config
%      uses binary_operators=[...,"^"] (not "**") and
%      unary_operators=["sin","cos","log","sqrt","exp"] (bare names, no
%      "np." prefix; "abs" is not configured at all). Unconverted, `guesses`
%      would have received strings PySR's own operator set can't parse —
%      likely a silent no-op or hard error, not a real warm-start.
%      FIXED: added _llm_expr_to_pysr_syntax() in the script, converting
