A more likely real cause, visible once you look at both timeout layers together:
    • The outer layer (ThreadPoolExecutor + future.result(timeout=300)) is the one governing the 300s tests-1–18 limit. 
    • The inner layer (_run_pysr_in_subprocess's own communicate(timeout=...)) uses a different, larger timeout — 900s/1100s per repro.yaml, visible in the subprocess worker's own defaults. 
    • When the outer 300s fires, the harness returns a synthetic "timed out" result and moves on to the next test — but the background thread running underneath is never actually stopped, because _kill_thread never worked (that's the bug we already patched — but we only deleted the broken call; we never gave the outer timeout a way to actually reach the subprocess). 
    • That means the abandoned thread's PySR subprocess keeps running with its own internal 900–1100s budget, invisible to the harness, silently competing for CPU with whatever test runs next — matching observ-10.txt's own speculation about Nernst (test 6) contending with an "orphaned Arrhenius process." 
The structural gap: proc (the actual subprocess handle) is a local variable buried inside _run_pysr_in_subprocess, three call layers below the outer timeout handler. The outer code has no reference to it at all — that's why the original fix reached for the hacky thread-injection trick (_kill_thread) instead of just killing the subprocess directly.
The real fix is to thread a shared handle out: have _run_pysr_in_subprocess register its proc into a mutable box passed down from the outer scope, so when the 300s method-timeout fires, the outer handler can call _kill_process_group() on the actual subprocess directly — no thread-killing needed at all.
